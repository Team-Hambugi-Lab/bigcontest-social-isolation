# LLM 역할과 안전장치 — 2026-10-26

> 서비스 플로우 [README.md](README.md)의 단계(0\~5)에서 LLM이 맡는 범위다. 팀 검토를 거쳐 모델, 개인정보·민감정보 처리, 보관 기간, 위기 감지 2단계를 정했다. 이 문서만 읽어도 LLM 부분을 이해할 수 있게 README의 관련 규칙을 함께 적었다.

**판단은 규칙이 하고, LLM은 말을 만든다.** 위험 특징, 티어, 위기 여부, 후보 통과, 기관 목록은 LLM 출력으로 정하지 않는다. LLM이 멈추거나 틀린 말을 해도 판단 결과는 그대로이고, 고정 문구로 같은 흐름을 이어 갈 수 있어야 한다.

## 1. 단계별 LLM 역할

한눈에 보기:

| 단계 | LLM 사용 | 활용 목적 | LLM 출력 | 판단하는 쪽 |
|---|---|---|---|---|
| 0 온보딩 | 씀 | 어려움을 편하게 말하게 하기 | 대화체 질문, 문항표 안의 선택지 제시 | 본인이 고른 선택지 → 규칙 |
| 1 분류 | 안 씀 | — | — | 위험 특징 사전 규칙 |
| 2 관찰 | 씀 | 짧은 안부로 변화 확인 | 체크인 질문, 자유 응답 요약 | 버튼 선택값 → 규칙 |
| 위기 감지 (모든 단계) | 씀 (2차) | 규칙이 놓친 위기 표현 잡기 | 위기 의심 예/아니요 + 근거 구절 | 1차 어휘 규칙, 확인 문항 → 규칙, 사람 |
| 3 탐지 | 안 씀 | — | — | 티어 결정표 (해당 범주 수, 본인 기준선 대비 악화) |
| 4 추천 | 씀 | 조건 확인, 추천 이유 설명 | 문항표 질문, 기관·사업 안내문 | `PASS_IF`(본인 선택지), `PRIORITY`, 기관 필터 |
| 5 후속 | 씀 | 이용 여부·도움 정도 확인 | 질문 | 선택지 → 기관·사업 ID로 기록 |
| 담당자 이관 | 씀 | 담당자가 상황을 빨리 파악 | 마스킹된 대화 요약 | 이관 여부는 규칙 |
| 지역 층 | 안 씀 | — | — | 관찰 우선 지역 규칙 (노출 지수와 활동 신호 비교) |

### 0 온보딩

- **목적:** 사용자가 어려움을 편하게 말하게 하고, 위험 특징은 본인이 고른 선택지로 확정한다.
- **역할:** 고정 문항을 대화체로 바꾸고, 자유 응답에 맞는 선택지를 보여 준다.
- **동작 순서**
  1. 규칙이 지금 물을 문항과 선택지 ID를 넘긴다.
  2. LLM이 사용자 연령대·말투에 맞게 질문한다.
  3. 자유 응답이 오면 위기 감지(아래)를 먼저 거친다.
  4. LLM이 문항표 안의 선택지를 보여 준다. "해당 없음 / 잘 모르겠어요"를 항상 함께 두고, 미리 선택해 두지 않는다.
  5. 본인이 고른 선택지를 규칙이 특징 코드로 바꾼다.
- **검증:** 출력에 문항표 밖의 선택지 ID가 있으면 버린다.
- **실패 시:** 문항과 선택지 원문을 그대로 보여 준다.

### 2 관찰 (체크인)

- **목적:** 짧은 안부로 본인 평소 상태와 달라진 점을 꾸준히 확인한다.
- **역할:** 체크인 인사와 질문을 만들고, 자유 응답을 요약한다.
- **동작 순서**
  1. 규칙이 이번에 물을 범주를 정한다 (1회 1\~2문항).
  2. LLM이 질문을 만든다.
  3. 악화 판단에 쓰는 값(지난주 외출 일수 등)은 **버튼 선택값으로만** 받는다.
  4. 자유 응답은 위기 감지를 거친 뒤 마스킹하고, LLM이 요약해 담당자 기록에 붙인다 (마스킹한 원문도 함께 남긴다).
- **검증:** 무응답·이동 수치·기준선 계산에 LLM 출력을 쓰지 않는다.
- **실패 시:** 고정 체크인 문항을 그대로 보낸다.

### 위기 감지 (모든 단계 공통, 2단계)

- **목적:** 위기 표현을 놓치지 않는다. 1차 규칙이 놓친 표현을 2차 LLM이 한 번 더 잡는다.
- **역할:** LLM은 2차 분류만 한다. 이관 결정은 규칙과 사람이 한다.
- **동작 순서**

  | 단계 | 방법 | 걸리면 | 안 걸리면 |
  |---|---|---|---|
  | 1차 규칙 | 모든 사용자 입력을 LLM보다 먼저 어휘 목록(2절)으로 검사 | LLM 응답을 만들지 않고 고정 문구로 109·119와 `CRISIS_LINE`을 안내한 뒤 지정 담당자에게 이관 | 2차로 |
  | 2차 LLM | 같은 입력을 "위기 의심 예/아니요 + 근거 구절" 형식으로 분류 | 고정 확인 문항("지난 2주 안에 죽고 싶거나 스스로를 해치고 싶다는 생각이 든 적이 있나요?")을 보내 본인 답을 받는다. 예, 응답 거부, 애매함이면 이관 (위험 특징 사전 "판단이 애매하면 위기 쪽") | 일반 대화 계속 |

- **검증:** LLM은 위기 의심을 **올릴 수만** 있고 내릴 수 없다. 1차에 걸린 입력은 LLM 판단과 상관없이 이관한다. 2차 출력이 형식 검사를 통과하지 못하면 "예"로 보고 확인 문항으로 넘긴다.

### 4 추천

- **목적:** 매핑표 조건을 대화로 확인하고, 규칙이 고른 기관을 쉬운 말로 설명한다.
- **역할:** [`note_check_questions.csv`](note_check_questions.csv)의 `QUESTION`을 말투만 바꿔 묻고, 통과한 기관·사업을 DB 필드로 안내한다.
- **동작 순서**
  1. 규칙이 `PRIORITY` 순으로 문항표 질문을 넘긴다.
  2. LLM이 묻고, 본인이 선택지로 답한다.
  3. 규칙이 `PASS_IF`로 통과 여부를 정하고, 지역·대상 연령·운영 상태로 기관을 거른다.
  4. LLM이 통과한 기관·사업의 ID와 필드(이름, 주소, 서비스, 기준일 `AS_OF`)로 안내문을 만든다.
- **검증:** 출력에 들어간 기관 ID가 후보 목록에 있는지, 전화번호·주소가 DB 값과 같은지 검사한다. 다르면 그 문장을 버리고 DB 필드를 그대로 보여 준다. 병명·약·치료 효과를 말하지 않고, 수치는 `SUPPORT_NEED_PCT` 같은 DB 값만 쓴다. `SUPPORT_NEED_PCT`는 청년 실태조사 값이라 청년에게만, 안내 문구의 근거로만 쓴다.
- **실패 시:** 문항표 원문과 DB 필드를 그대로 보여 준다.

### 5 후속

- **목적:** 연계한 서비스를 이용했는지, 도움이 됐는지 확인한다.
- **역할:** 질문만 만든다.
- **동작 순서:** LLM이 묻는다 → 본인이 선택지로 답한다 → 규칙이 기관·사업 ID로 기록한다.

### 담당자 이관 요약 (위기·연락 두절)

- **목적:** 담당자가 대화 전체를 읽지 않고도 상황을 빨리 파악하게 한다.
- **역할:** 마스킹된 대화를 요약한다.
- **검증:** 요약에 판정(위기 여부, 티어)을 넣지 않는다. 규칙의 판정 결과는 별도 필드로 붙인다.

## 2. 위기 표현 어휘 목록 (아이디어)

실제 목록 파일은 아직 만들지 않았다. 구성 방향만 정한다.

| 유형 | 예시 표현 | 근거 |
|---|---|---|
| 직접 표현 | 죽고 싶다, 자살, 목숨을 끊다 | 위험 특징 사전 `MIND_SUICIDE_IDEA` 정의, PHQ-9 9번 문항 |
| 간접 표현 | 사라지고 싶다, 다 끝내고 싶다, 없어지면 편할 텐데, 내가 짐만 된다 | 자살예방 게이트키퍼 교육(보고듣고말하기)의 언어적 경고 신호 |
| 계획·수단 | 약을 모아 뒀다, 뛰어내리다, 유서 | 같은 교육의 계획 단계 신호 |
| 작별 행동 | 물건을 정리했다, 마지막 인사, 그동안 고마웠다 | 같은 교육의 행동 신호 |
| 자해·시도 | 손목을 긋다, 약을 많이 먹었다 | 위험 특징 사전 `MIND_SUICIDE_ATTEMPT` 정의 |

- **놓치지 않는 쪽(재현율 우선)으로 만든다.** 1차에서 잘못 걸린 경우는 담당자가 확인한다.
- **정규화한 뒤 비교한다.** 띄어쓰기, 맞춤법 오류, 초성 줄임말을 맞춘 뒤 대조한다.
- **부정문도 빼지 않는다.** "죽고 싶진 않아" 같은 표현은 1차에서 제외하지 않고 2차로 넘긴다.
- **운영 중 갱신한다.** 2차에서 걸렸는데 1차가 놓친 표현은 담당자 확인을 거쳐 목록에 추가한다. 실제 목록은 정신건강 전문가 검토를 받는다.

## 3. 모델: Kanana-2 30B-A3B Instruct (자체 운영)

카카오의 오픈 웨이트 모델 [`kakaocorp/kanana-2-30b-a3b-instruct-2601`](https://huggingface.co/kakaocorp/kanana-2-30b-a3b-instruct-2601)(2026-01-15 공개)을 **국내 클라우드에 직접 올려** 운영한다.

| 기준 | 판단 |
|---|---|
| 학습 차단 | 대화가 모델 제공자에게 가지 않는다. 운영 서버 안에서만 처리하므로 제공자가 대화를 학습에 쓸 수 있는 경로가 없다 |
| 데이터 위치 | 공공기관용 국내 클라우드에 두면 국외 이전이 없다 |
| 품질 | 모델 카드 기준 KMMLU 68.26, HAERAE-Bench 75.57, KoMT-Bench 8.21. 같은 크기의 Qwen3-30B-A3B-Instruct-2507(KMMLU 67.56, HAERAE 53.41, KoMT 8.49)과 비슷하거나 한국어 지식에서 높다. 우리 LLM 일(질문 바꾸기, 요약, 설명, 위기 2차 분류)은 짧고 가벼워서 충분하다 |
| 비용 | 토큰 과금이 아니라 서버 비용이다. 전체 30B 중 활성 파라미터가 3B인 전문가 혼합(MoE) 구조라 같은 품질의 밀집 모델보다 추론 비용이 낮다. 기본 컨텍스트 32,768 토큰으로 대화 몇 턴에 충분하다 |
| 라이선스 | Kanana License. 자기 서비스의 개발·운영은 상용 라이선스 없이 가능하다(§4.3). 제3자에게 API·클라우드로 제공하거나, SI·온프레미스 솔루션으로 제공하거나, 기기에 넣어 제공하면 카카오의 별도 상용 라이선스가 필요하다(§4.1). 직전 달 월간 이용자가 1천만 명을 넘는 경우도 별도 라이선스 대상이다(§4.2). "Powered by Kanana"를 웹사이트·UI·문서에 표시해야 한다(§3.1(v)) |

- **운영 형태:** 지자체가 자기 서비스로 직접 운영하면 §4.3에 해당한다. 업체가 지자체에 SI로 구축해 주는 형태라면 §4.1(ii)에 해당할 수 있어 카카오와 상용 계약이 필요하다.

**비교한 대안**

| 모델 | 장점 | 고르지 않은 이유 |
|---|---|---|
| Upstage Solar Pro (API) | 한국어 품질이 좋고 API 단가가 낮다. 유료 API 입출력은 별도 사전 동의 없이 서비스 개선·학습에 쓰지 않는다 (이용약관 제22조 5항) | 개인정보처리방침상 서비스 이용 중 입력한 대화와 파일이 미국의 Amazon Web Services, Microsoft Azure로 국외 이전된다. 민감정보를 다루기에 불리하다 |
| 네이버 HyperCLOVA X (CLOVA Studio) | 한국어 품질이 좋고 공공기관용 클라우드가 있다 | API 입력의 학습 활용 여부를 공식 문서에서 확인하지 못했다. 쓰려면 학습 제외 조건을 계약서로 확인해야 한다 |
| LG EXAONE | 한국어 성능이 좋다 | 비상업 라이선스(NC)다 |
| Kanana-2 3B Instruct | 더 가볍다 (KMMLU 3B base 47.92) | 30B-A3B보다 한국어 지식 점수가 크게 낮다. 서버 자원이 부족한 시범 단계의 대체안으로 둔다 |

**API 모델로 바꿀 경우의 조건.** 개인정보보호위원회 「생성형 AI 개발·활용을 위한 개인정보 처리 안내서」(2025-08)는 서비스형 LLM을 쓸 때 기업용 약관이나 데이터 처리 부속서(DPA)로 데이터 보호 요구사항을 계약으로 확보하고 국외 이전 여부를 검토하라고 권고한다. 이에 따라 "입력·출력을 학습에 쓰지 않음, 보관하지 않음(또는 보관 기간 명시), 국내 처리"를 계약으로 확인한 모델만 쓴다.

**시연.** 제출 범위에서는 실제 모델을 돌리지 않았다. 발표자료의 대화는 "설계상 LLM이 이렇게 동작한다"는 예시이고, 슬라이드에 "예시 대화(합성)"로 표시한다 (10/26 결정). 대화 문장은 사람이 직접 썼고, 합성 방법은 [`scenarios.md`](scenarios.md) "합성 방법"에 있다.

## 4. 개인정보·민감정보 처리

### 4-1. 처음에 받는 동의

온보딩 첫 화면에서 아래를 나눠 받는다. 개인정보보호위원회 안내서도 민감정보는 별도 동의 또는 법적 근거가 있어야 처리할 수 있다고 정리한다.

| 동의 | 내용 | 거부하면 |
|---|---|---|
| 개인정보 수집·이용 (필수) | 연령대, 거주 시군구·행정동, 연락 수단. **대화 중 나온 개인정보는 마스킹해서 보관한다**는 점을 함께 알린다 | 서비스를 이용할 수 없다 |
| 민감정보 수집·이용 (선택, 별도) | 건강·정신건강 상태 등 위험 특징 판단에 쓰는 정보. **사용자에게 맞춘 관찰과 기관 추천을 위해** 받는다고 알린다 | 서비스는 계속된다. 해당 범주는 묻지 않고, 거부를 위험 신호로 세지 않는다 (정신건강·경제 같은 민감 범주는 따로 동의받는다는 설계 원칙) |
| 기관 연계 시 정보 제공 (선택) | 연계를 요청할 때 기관에 넘기는 항목(이름, 연락처, 필요한 도움) | 기관 정보 안내까지만 한다 |
| 이동 요약 수집 (선택) | 휴대폰 안에서 계산한 요약값만 | 체크인만으로 관찰한다 |

- 상담 서비스의 민감정보 동의서들도 "동의를 거부할 수 있으나 거부하면 이용에 제한이 있을 수 있다"는 점과 보유 기간을 함께 적는 방식을 쓴다. 우리도 각 동의에 거부 시 영향과 보유 기간(4-3절)을 함께 적는다.

### 4-2. 마스킹 후 저장

대화에는 민감정보와 식별 정보가 섞일 수 있다. 원문을 그대로 두지 않고 **마스킹한 뒤 서비스 DB에 저장**한다.

1. 사용자 입력이 들어오면 위기 1차 검사를 먼저 한다 (지연 없이 이관하기 위해).
2. 규칙으로 식별 정보를 가린다: 이름, 전화번호, 주민등록번호, 행정동보다 자세한 주소, 계좌·카드번호, 대화에 나온 다른 사람의 이름 → `[이름]`, `[연락처]` 같은 자리표시.
3. LLM에는 가린 문장만 넘긴다.
4. 서비스 DB에는 가린 원문, LLM 요약, 판정 결과(선택지 ID, 특징 코드, 티어)만 저장한다.

- 가명·마스킹 처리를 해도 건강 정보는 여전히 민감정보로 다룬다. 마스킹은 노출 위험을 줄이는 조치이고, 별도 동의를 대신하지 않는다.
- 시연에는 페르소나 합성 데이터만 넣는다. 실제 개인 응답은 넣지 않는다.

**LLM에 넘기는 입력**

| 넘긴다 | 넘기지 않는다 |
|---|---|
| 지금 묻는 문항과 선택지, 직전 몇 턴의 마스킹된 대화 | 이름, 연락처, 생년월일 같은 식별 정보 (가명 ID만 쓴다) |
| 사용자의 특징 코드와 연령대 (말투와 설명을 맞추는 데 필요한 만큼) | 행정동보다 자세한 위치, 이동·체류 원자료 |
| 통과한 후보 기관·사업의 DB 필드 (이름, 주소, 서비스, 기준일) | 티어 이력 전체, 담당자 메모, 다른 사용자의 정보 |

### 4-3. 보관 기간

| 기록 | 기간 | 근거 |
|---|---|---|
| 연계·사례 기록 (특징 코드, 티어 이력, 기관 연계·이용 기록, 담당자 이관 기록) | **5년**이 지나면 파기 | 「사회보장급여의 이용·제공 및 수급권자 발굴에 관한 법률」 제34조: 보장기관의 장은 사회보장정보를 5년이 지나면 파기해야 한다. 지원대상자 보호에 필요한 정보는 대통령령에 따라 5년을 넘겨 보유할 수 있다 |
| 마스킹한 대화 원문 | **90일** 뒤 파기 (운영 가정) | 「개인정보 보호법」 제21조: 보유 기간이 지나거나 목적을 달성하면 지체 없이 파기해야 한다. 원문은 판정 근거와 이관 요약을 확인하는 용도라 판정·요약에 반영된 뒤에는 오래 둘 이유가 없다 |
| LLM 요약 | 연계·사례 기록과 같이 5년 | 연계·사례 기록의 일부 |
| 모델 제공자 쪽 기록 | 없음 | 자체 운영이라 제공자에게 대화가 가지 않는다 |
| 탈퇴한 사용자 | 대화 원문은 즉시 파기, 연계 기록은 5년 기준 적용 | 위 두 조문 |

- 90일은 법정 기간이 아니라 우리가 정한 운영 기준이다. 참고로 민간 AI 통화 서비스(SK텔레콤 에이닷)는 통화 내용과 요약을 6개월 보관한다고 알려져 있다.
- 파기는 전자 기록을 복구할 수 없는 방법으로 한다.

## 5. 잘못된 답에 대한 안전장치

1. **문항표 밖에서 판정하지 않는다.** 조건 확인의 통과 여부는 본인이 고른 선택지로 정한다. LLM이 "조건을 충족한 것 같다"고 말해도 통과로 처리하지 않는다. 선택지로 확인되지 않으면 보류("확인 대기")로 두고 다음 체크인에서 다시 묻는다.
2. **위기 확인은 LLM보다 먼저 한다.** 1차 어휘 규칙에 걸리면 LLM 응답을 만들지 않고 고정 문구로 안내하며 사람에게 이관한다. LLM은 2차에서 위기 의심을 올릴 수만 있다 (1절 위기 감지).
3. **없는 기관을 만들지 않는다.** 기관·사업 안내에는 넘겨받은 후보의 ID만 쓴다. 출력의 ID가 후보 목록에 있는지 검사하고, 없거나 전화번호·주소가 DB 값과 다르면 그 문장을 버리고 DB 필드를 그대로 보여 준다.
4. **진단하지 않는다.** 병명, 약, 치료 효과를 말하지 않는다. 수치는 DB 값만 쓰고 새 숫자를 만들지 않는다.
5. **실패하면 고정 문구로 간다.** 응답이 없거나 형식 검사를 통과하지 못하면 문항표 원문과 DB 필드를 그대로 보여 준다. 흐름은 멈추지 않는다.
6. **시연 전에 금지 출력을 시험한다.** [`scenarios.md`](scenarios.md)의 대화에 위기 표현, 모호한 조건 응답, 없는 기관 요청을 섞어 위 1\~5가 지켜지는지 확인한다.
